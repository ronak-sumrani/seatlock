# ADR-011: Schema-per-service on one Postgres

## Context
Each service must own its data (spec §4, rule 1): no shared tables and no cross-service SQL. If
that rule is only a convention, one shortcut query from Booking into `inventory.seats` quietly
couples the two services, and nobody notices until a schema change breaks Booking. We also need one
process that can read everything: the invariant checker (I1, I2, R1-R3) has to join seats,
bookings and payments to prove that nothing went wrong.

At the same time, this is a laptop-sized project. Running five Postgres servers to get isolation
would cost RAM and setup time and teach nothing new.

## Decision
One Postgres 16 instance, database `seatlock`, one schema per service, and **the database enforces
the boundary**:

- One login role per deployable. It owns its schema(s) and has no rights anywhere else:
  `user_catalog_user` owns `auth` and `catalog` (two modules, one deployable, spec §4),
  `inventory_user` owns `inventory`, `booking_user` owns `booking`, `payment_user` owns `payment`.
- `REVOKE ALL ... FROM PUBLIC` on the database and on schema `public`, so a role has only what it is
  granted explicitly.
- `checker_ro` gets `USAGE` and `SELECT` on every schema, plus `ALTER DEFAULT PRIVILEGES` for each
  owner, so tables that Flyway creates later are readable too. Its sessions start with
  `default_transaction_read_only = on`.
- Each service runs Flyway as its own role, with `flyway_schema_history` in its own schema.
  Schemas are created by the init script (`deploy/postgres/init/01-schemas-and-roles.sh`), not by
  Flyway, because service roles may not create schemas.

## Alternatives considered
- **One database user for everything.** Simplest, but the boundary would be a convention only,
  and a stray cross-schema join would work fine until it broke something. Rejected: the point is
  that the boundary is *provable*.
- **One Postgres database or server per service.** Gives the strongest isolation, including
  separate connection limits and failure domains. But it means five servers (or databases with
  separate connection pools) on a laptop, and the invariant checker would then need
  cross-database queries (dblink/FDW) or a copy of the data. Rejected for this scale. Because no
  service queries another schema, a later split only means changing the JDBC URL.
- **A separate role per schema for user-catalog (`auth_user` + `catalog_user`).** That would give
  isolation even between auth and catalog, but it needs two DataSources and two Flyway runs in one
  service. Deferred: if auth becomes its own service, it gets its own role then.

## Consequences
- Good: "each service owns its data" is checked by Postgres on every query. A cross-schema query
  fails with `permission denied for schema` the first time it runs, in tests or locally.
- Good: the invariant checker can join across all schemas with a role that can't write.
- Bad: one Postgres is a shared failure domain and a shared load domain. A slow query in Booking
  competes with Inventory's hot path for CPU, I/O and `max_connections`. We accept this for the
  demo and list it as a known limitation.
- Bad: the init script runs only on an empty data volume. Changing roles means
  `docker compose down -v` locally, and a real migration path (a superuser-run script) later.
- Neutral: service roles can still change their own schema freely, which is what Flyway needs.

## How it is tested
- `libs/common/.../SchemaIsolationIT` (Testcontainers, runs the same init script that Compose
  uses): each owner can read and write its own schema(s); each owner gets SQLSTATE `42501` on
  SELECT/INSERT/CREATE in every other schema; nobody can create in `public`; `checker_ro` can read
  tables created *after* init in every schema, and it can't write even after it turns read-only
  off for its session. It was mutation-checked: removing the default privileges from the script
  makes the checker test fail.
- Each service's `*ApplicationIT` starts the app logged in as its own role (not the superuser)
  and asserts that Flyway applied V1 in its own schema.
